# Communication faults with and without the protection layer

Generated by the campaign. Do not edit by hand.

One CRC plus counter plus timeout implementation, configured as AUTOSAR E2E and as PROFIsafe, run against the same eight communication faults as the bare protocol. See `docs/STANDARDS_MAPPING.md` for the vocabulary, and note that this models the mechanism rather than implementing either standard.

Latency is in **exchanges** for the protected runs and in **steps** for the bare runs. They are the same unit here, one command per step, but they are named differently because they are counted at different layers.

| Fault | Bare protocol | E2E | PROFIsafe | What the layer bought |
|---|---|---|---|---|
| FLT-C01 | rejected on arrival | ERROR @ 1 | ERROR @ 1 | nothing: the bare protocol already rejected it on arrival |
| FLT-C02 | rejected on arrival | ERROR @ 1 | ERROR @ 1 | nothing: the bare protocol already rejected it on arrival |
| FLT-C03 | step 10 | ERROR @ 1 | ERROR @ 1 | detected 9 steps earlier, before the payload reaches the device |
| FLT-C04 | step 10 | ERROR @ 1 | ERROR @ 1 | detected 9 steps earlier, before the payload reaches the device |
| FLT-C05 | rejected on arrival | ERROR @ 1 | ERROR @ 1 | nothing: the bare protocol already rejected it on arrival |
| FLT-C06 | step 10 | ERROR @ 1 | ERROR @ 1 | detected 9 steps earlier, before the payload reaches the device |
| FLT-C07 | rejected on arrival | ERROR @ 1 | ERROR @ 1 | nothing: the bare protocol already rejected it on arrival |
| FLT-C08 | not detected | WRONG_ID @ 1 | **not detected** | closes a fault the bare protocol never detects; **the two profiles disagree**, see below |

## Where the two profiles disagree, and why

FLT-C08 is a correctly formed, correctly checksummed reply about the wrong quantity. Neither a CRC nor a sequence counter can catch it: nothing is corrupted and nothing is out of order.

**E2E detects it.** A Data ID identifies a *data element*, so a reply carrying a temperature has a different Data ID from one carrying a speed, and the mismatch is visible.

**PROFIsafe does not.** An F_Destination_Address identifies a *device*. Every message on the link to that device carries the same address, so a reply about the wrong quantity from the right device passes every check.

The two mechanisms are routinely presented as equivalent, and for corruption, repetition, loss and delay they are. For binding a reply to the question it answers they are not, and the difference is a property of what the identifier identifies rather than of how strong it is. Closing it under PROFIsafe is an application layer job.
